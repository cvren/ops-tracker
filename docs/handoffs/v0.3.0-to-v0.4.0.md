# v0.3.0 to v0.4.0 Handoff

## Current shipped baseline

- `v0.3.0` remains the shipped release marker in this repo
- `package.json` remains on `0.3.0`
- Local tag `v0.3.0` exists
- The shipped `v0.3.0` runtime exposed `admin`, `member`, and `viewer`
- Manager-console mutations were admin-only in shipped behavior
- Recurring generation was manual through `Generate now`
- `RecurringExecution` in the shipped baseline was the narrower execution record, not the full `v0.4.0` ledger contract
- `corepack pnpm recurring:tick` does not exist in the shipped release

## Contract baseline still fixed

- Theme: `Delegation you can trust, automation you can inspect`
- Primary contract doc: `docs/contracts/v0.4.0-operating-contract.md`
- `v0.4.0` role model stays fixed to `admin`, `manager`, `member`, and `viewer`
- Manager responsibilities stay fixed to dashboard / manager queue usage, bulk actions, template management, recurring management, execution history, and rerun execution
- Manager exclusions stay fixed to workspace root settings, membership-wide management, manager re-delegation, and scheduler configuration
- `RecurringExecution` stays fixed as the source-of-truth ledger with explicit status, timing, trigger, and generation fields
- Manual `Generate now` and scheduled recurring execution must share one pipeline
- Official scheduled entrypoint stays fixed to `corepack pnpm recurring:tick`
- Duplicate-safe execution is required
- Rerun is required
- Skip remains optional

## Current repo checkpoint after v0.4.0 Phase 4 closeout

- `Membership.role` now includes `ADMIN`, `MANAGER`, `MEMBER`, and `VIEWER`
- Admins can grant manager access and revoke it back to member through the existing workspace membership flow
- Managers can now use dashboard, manager queues, bulk actions, templates, recurring schedules, and manual `Generate now`
- Membership-wide management remains admin-only
- Members keep the normal collaboration flow
- Viewers remain read-only
- Activity history now records `MANAGER_ROLE_GRANTED` and `MANAGER_ROLE_REVOKED`
- `RecurringExecution` now implements the contract shape with workspace, status, timing, trigger provenance, failure detail, and generated-task count
- Manual `Generate now` now creates `RUNNING` execution rows and resolves them to `SUCCESS` or `FAILED`
- Generated tasks now link back to their execution through `Task.recurringExecutionId`
- Templates now show recurring execution history directly from the ledger, including seeded `SUCCESS`, `FAILED`, `SKIPPED`, and `RUNNING` rows
- Failed executions can now be rerun by managers, and rerun writes a fresh execution row for the same slot
- Activity history now records `RECURRING_EXECUTION_STARTED`, `RECURRING_EXECUTION_SUCCEEDED`, `RECURRING_EXECUTION_FAILED`, and `RECURRING_EXECUTION_RERUN`
- `corepack pnpm recurring:tick` now exists and runs active due schedules through the same recurring execution pipeline as manual `Generate now` and rerun
- Scheduled attempts now write `SYSTEM` executions into the ledger with duplicate-safe slot claims and visible failure history
- Seed data and automated coverage now include due scheduled-success demo data plus rerunnable scheduled-failure samples
- Fresh-seed tick truth is one new `SYSTEM` success for `Scheduled inventory digest`, one skipped due slot for `Recovery retry drill`, and the original failed scheduled execution staying visible until a manager reruns it
- `SKIPPED` remains contract-valid and seed-visible, but current scheduled skip suppression is reported by tick output instead of writing a new ledger row and no manager skip action is exposed
- Current branch-head package version is `0.4.0`, while shipped `v0.3.0` remains the latest published release until the human PR / merge / tag / GitHub Release steps complete

## v0.4.0 phase order and acceptance snapshot

1. `ops-tracker v0.4.0 Phase 0 — Operating Contract`
   - fixed the repo contract without claiming runtime delivery
2. `ops-tracker v0.4.0 Phase 1 — Safe Delegation`
   - implemented locally through the four-role workspace model and delegated manager-console boundary
3. `ops-tracker v0.4.0 Phase 2 — Execution Ledger`
   - implemented locally through the contract-shape `RecurringExecution` ledger, execution history UI, task linkage, failure visibility, and failed-slot rerun
4. `ops-tracker v0.4.0 Phase 3 — Controlled Scheduled Execution`
   - implemented locally through `corepack pnpm recurring:tick`, `SYSTEM` ledger rows, duplicate-safe slot claims, and shared scheduled/manual pipeline behavior
5. `ops-tracker v0.4.0 Phase 4 — Release Closeout`
   - final: align docs, release notes, validation, and delivered `v0.4.0` scope

## v0.4.0 non-goals

- full RBAC matrix
- custom role builder
- advanced capability editor
- background worker or queue orchestration platform
- holiday calendar
- business-day due calculation
- advanced RRULE recurrence
- Slack, email, or push notification expansion
- analytics, BI, or forecasting
- workflow automation builder
- organization hierarchy

## Risks to avoid

- Do not widen manager permissions beyond the contract exclusions already fixed in `Phase 0`
- Do not move manager-role source of truth away from `Membership.role`
- Do not treat `RecurringExecution` as a debug log after `Phase 2`; it is now the operating ledger
- Do not split manual and scheduled execution into separate pipelines
- Do not introduce a worker platform when `v0.4.0` only needs a single tick entrypoint
- Do not claim planned `Phase 3` or `Phase 4` behavior is already shipped in `v0.3.0`
