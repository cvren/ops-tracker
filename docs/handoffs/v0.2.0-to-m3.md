## Known limits

- No email, Slack, push, or realtime delivery
- No attachment support
- No comment edit, delete, or threading model
- No advanced notification preferences
- No analytics, SLA, escalation, recurring tasks, or automation builder
- Playwright validation is intentionally serial and single-worker because the seeded flow mutates shared workspace state

## Architectural constraints

- `Membership.role` remains the effective authorization boundary
- The product stays single-workspace in `v0.2.0`
- `ActivityEvent` is the source of truth for task-scoped history and notification fan-out
- Notification fan-out stays centralized around shared activity helpers; do not add a generic queue unless M3 explicitly requires it
- Structured mentions remain the preferred approach; do not replace them with brittle free-text parsing
- `test:e2e` and `build` must stay serial in the same worktree because both touch `.next`
- `pnpm` is pinned to `10.19.0` and build-script policy lives in `pnpm-workspace.yaml`

## Non-goals carried forward

- Email notifications
- Slack notifications
- Realtime or websocket updates
- Attachments
- Comment edit/delete/threading
- Advanced notification preferences
- Analytics, SLA, and escalation tooling
- Webhook or automation builder scope

## Recommended implementation order for M3

1. Strengthen manager visibility on top of current `Task`, `ActivityEvent`, and saved-view data
2. Add workload, aging, and bottleneck visibility without replacing the existing M1/M2 task flow
3. Introduce carefully scoped bulk actions only after queue visibility is stable
4. Evaluate task templates or recurring-task support only after the bulk flow is clear
5. Add optional integrations only after the in-product control-tower behavior remains the source of truth

## M3 acceptance criteria draft

- Manager dashboard shows workload, aging, and bottleneck signals without weakening the current operator flow
- Users can spot stale review queues and long-running ownership gaps quickly
- Bulk actions, if added, respect workspace guard and existing review rules
- Template or recurring-task support, if added, preserves the current task lifecycle semantics
- `v0.2.0` ownership, review, comment, timeline, and inbox flows remain intact
