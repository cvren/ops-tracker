# v0.4.0 to v0.5.0 Handoff

## Current state

- `ops-tracker v0.4.0` is release-ready on the current branch head
- `package.json` is `0.4.0` on the release-ready branch head
- The latest shipped release marker is still `v0.3.0` until PR / merge / tag `v0.4.0` / GitHub Release publication complete
- The current repo delivers the four-role workspace model, the `RecurringExecution` source-of-truth ledger, and the shared manual / scheduled recurring pipeline

## What is verified

- Local validation covers install, migrations, seed, lint, typecheck, unit tests, Playwright e2e, build, and `corepack pnpm recurring:tick`
- Fresh-seed scheduled truth is:
  - `Due: 2`
  - `Succeeded: 1`
  - `Failed: 0`
  - `Skipped: 1`
- The scheduled failure demo path remains inspectable and rerunnable through the manager console

## What shipped in v0.4.0

- `Phase 0` fixed the operating contract, role model, ledger contract, scheduler entrypoint, and non-goals
- `Phase 1` delegated the manager console safely through the workspace-scoped `manager` role
- `Phase 2` made `RecurringExecution` the execution ledger for manual runs and reruns
- `Phase 3` connected scheduled `SYSTEM` execution to the same duplicate-safe recurring pipeline through `corepack pnpm recurring:tick`
- `Phase 4` reconciled docs, validation, release notes, and forward handoff material to one release-ready truth

## Known limits

- `/workspace` stays read-only for non-admin roles and membership mutation remains admin-only
- `SKIPPED` is contract-valid and UI-visible, but there is still no manager skip action and tick-suppression skips do not create fresh ledger rows
- Execution history still lives in the templates console and task origin panel; there is no dedicated cross-schedule history screen
- `v0.4.0` still does not include notification fan-out, worker orchestration, advanced RRULE recurrence, holiday handling, or analytics

## Architectural constraints

- Keep `Membership.role` as the single effective workspace role boundary
- Keep `RecurringExecution` as the source-of-truth recurring ledger
- Keep manual generate, scheduled tick, and rerun on one shared execution pipeline
- Keep duplicate safety anchored on `recurringScheduleId + scheduledFor`
- Keep scheduled automation as a single tick entrypoint instead of a worker platform unless a future contract explicitly changes that boundary

## Non-goals carried forward

- full RBAC matrix
- custom role builder
- advanced capability editor
- background worker or queue orchestration platform unless a future contract explicitly approves it
- holiday calendar
- business-day due calculation
- advanced RRULE recurrence
- Slack, email, or push notification expansion
- analytics, BI, or forecasting
- workflow automation builder
- organization hierarchy

## Recommended implementation order for v0.5.0

1. Decide whether `v0.5.0` is an operator-experience release, a recurring-operations release, or a different scope entirely.
2. If recurring operations expand, resolve `SKIPPED` runtime semantics and the execution-history surface before adding new scheduling power.
3. If manager workflows expand, preserve the existing four-role boundary and keep `Membership.role` as the only effective role source of truth.
4. Only after those boundaries are explicit, consider any new recurring recovery or reporting surfaces.

## v0.5.0 acceptance criteria draft

- A single written contract exists before implementation begins.
- Any recurring expansion keeps `RecurringExecution` as the source-of-truth ledger.
- Any manager-surface expansion preserves the existing four-role model unless the contract explicitly changes it.
- New validation and docs describe the same delivered boundary.
- New hosted CI requirements are observed and recorded before release closeout.
