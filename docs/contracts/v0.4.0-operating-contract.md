# v0.4.0 Operating Contract

## Intent

`ops-tracker v0.4.0 Phase 0 — Operating Contract` locks the durable boundaries for the `v0.4.0` release before implementation closes.

Its fixed theme is:

`Delegation you can trust, automation you can inspect`

`Phase 0` exists to fix:

- who is allowed to do what
- what recurring execution record becomes the ledger
- how manual and scheduled execution must relate
- what `v0.4.0` will not become

This document is a contract for the implementation phases. It does not claim that the shipped `v0.3.0` runtime already satisfies it.

## Role model

- `v0.4.0` proceeds with exactly four product roles:
  - `admin`
  - `manager`
  - `member`
  - `viewer`
- `v0.4.0` does not introduce a separate capability matrix
- `v0.4.0` does not introduce a custom role builder
- `v0.4.0` does not introduce an advanced capability editor
- Current repo note:
  - shipped `v0.3.0` runtime used `admin`, `member`, and `viewer`
  - the current repo now implements `manager` as a workspace-scoped runtime role through `Membership.role`
  - the shipped release marker still remains `v0.3.0` until humans complete PR / merge / tag `v0.4.0` / GitHub Release publication

## Manager responsibilities

`manager` is the delegated operator for manager-console work in `v0.4.0`.

The role is responsible for:

- dashboard usage
- manager queue usage
- bulk actions
- template management
- recurring management
- execution history visibility
- rerun execution

## Manager exclusions

`manager` does not own or control:

- workspace root settings
- membership-wide management
- manager permission re-delegation
- system-level scheduler configuration

These exclusions are part of the contract, not optional defaults.

## RecurringExecution ledger

`RecurringExecution` is the `v0.4.0` recurring execution ledger.

It is not just a log row. It is the source of truth for what the system attempted, when it attempted it, how it ended, and what it produced.

Required contract fields:

| Field | Contract |
| --- | --- |
| `id` | Stable execution identifier |
| `recurringScheduleId` | The schedule this execution belongs to |
| `workspaceId` | Workspace boundary for the execution |
| `status` | One of `RUNNING`, `SUCCESS`, `FAILED`, `SKIPPED` |
| `scheduledFor` | The run slot the execution is answering |
| `startedAt` | When execution work began |
| `finishedAt` | When execution work finished or stopped |
| `errorMessage` | Failure detail when status is `FAILED` |
| `generatedTaskCount` | Number of tasks produced by the execution |
| `triggeredBy` | One of `SYSTEM` or `USER` |
| `triggeredByUserId` | User actor for manual or rerun cases; null for pure system execution |
| `createdAt` | Ledger row creation timestamp |
| `updatedAt` | Ledger row update timestamp |

Current repo note:

- shipped `v0.3.0` schema used the narrower `RecurringExecution(scheduleId, scheduledFor, executedAt, createdTaskId)` model
- the current repo now implements the contract-shape ledger for manual `USER` executions, scheduled `SYSTEM` executions, and reruns
- execution history now reads from this ledger and generated tasks link back to it
- `corepack pnpm recurring:tick` now exists and routes scheduled execution through the same duplicate-safe pipeline as manual `Generate now`
- `SKIPPED` remains part of the contract shape, seeded demo data, and status palette, but current scheduled skip suppression is summary-only unless a real execution row already exists
- current branch-head note:
  - `package.json` is now prepared at `0.4.0` for release closeout
  - shipped `v0.3.0` remains the latest published release until tag and GitHub Release publication

## Execution pipeline invariants

- Manual `Generate now` and scheduled recurring execution must use the same core execution pipeline
- The pipeline must be duplicate-safe
- Every execution attempt must be representable in `RecurringExecution`
- Failures must remain inspectable after the attempt ends
- Rerun support is required
- Skip support is optional
- If skip is added later, it must be recorded through the same ledger model rather than hidden outside it
- Current repo note before `Phase 4`:
  - seeded history includes inspectable `SKIPPED` rows and a seeded `RECURRING_EXECUTION_SKIPPED` activity sample
  - scheduled tick can report `SKIPPED` outcomes when a due slot is suppressed by existing slot state
  - those tick-summary skips do not currently create a fresh `RecurringExecution` row
  - no manager-facing skip action is exposed

## Scheduler entrypoint

- The official scheduled recurring entrypoint for `ops-tracker v0.4.0 Phase 3 — Controlled Scheduled Execution` is `corepack pnpm recurring:tick`
- Scheduled automation is treated as a single tick trigger, not as a worker or orchestration platform
- If an internal route, webhook, or adapter is added later, it must stay a thin wrapper over the same execution pipeline
- The external scheduler is not the source of truth; the application ledger is

## v0.4.0 phase order

1. `ops-tracker v0.4.0 Phase 0 — Operating Contract`
2. `ops-tracker v0.4.0 Phase 1 — Safe Delegation`
3. `ops-tracker v0.4.0 Phase 2 — Execution Ledger`
4. `ops-tracker v0.4.0 Phase 3 — Controlled Scheduled Execution`
5. `ops-tracker v0.4.0 Phase 4 — Release Closeout`

Dependency rule:

- `Phase 1` depends on `Phase 0`
- `Phase 2` depends on `Phase 0` and `Phase 1`
- `Phase 3` depends on `Phase 0`, `Phase 1`, and `Phase 2`
- `Phase 4` closes the implemented scope after `Phase 1`, `Phase 2`, and `Phase 3`

## Non-goals

- full RBAC matrix
- custom role builder
- advanced capability editor
- background worker or queue orchestration platform
- holiday calendar
- business-day due calculation
- advanced RRULE recurrence
- Slack, email, or push notification expansion
- analytics, BI, or forecasting
- workflow automation builder
- organization hierarchy

## Risks to avoid

- widening delegated permissions before the exclusion boundary is fixed in runtime
- treating the ledger as an incidental debug table instead of the execution source of truth
- building separate manual and scheduled execution paths that drift over time
- introducing queue or worker infrastructure when `v0.4.0` only requires a single tick entrypoint
- claiming contract-only behavior as already shipped behavior
- changing `package.json` to `0.4.0` before the implementation and closeout are real

## Acceptance criteria overview

- `ops-tracker v0.4.0 Phase 0 — Operating Contract`
  - contract doc exists
  - repo docs align to it
  - current shipped `v0.3.0` truth remains clearly separated
- `ops-tracker v0.4.0 Phase 1 — Safe Delegation`
  - `manager` becomes a real delegated runtime role
  - dashboard, queues, bulk actions, templates, and recurring management are delegated safely
  - manager exclusions remain blocked
- `ops-tracker v0.4.0 Phase 2 — Execution Ledger`
  - `RecurringExecution` matches this ledger contract
  - history reads from the ledger
  - manual attempts capture trigger provenance
  - generated tasks link back to the execution that created them
  - failure detail is readable and rerun creates a fresh execution record
- `ops-tracker v0.4.0 Phase 3 — Controlled Scheduled Execution`
  - `corepack pnpm recurring:tick` exists
  - scheduled and manual execution share one core pipeline
  - active due schedules are selected with `nextRunAt <= now`
  - `SYSTEM` execution is visible in the ledger
  - duplicate-safe execution is enforced
  - rerun works from inspectable execution outcomes
- `ops-tracker v0.4.0 Phase 4 — Release Closeout`
  - docs, tests, and release notes describe the same delivered `v0.4.0` boundary
  - validation results are recorded
  - current-head GitHub-hosted `ci` is observed or blocked explicitly
  - `docs/handoffs/v0.4.0-to-v0.5.0.md` records the post-release starting point
  - remaining blockers are explicit
