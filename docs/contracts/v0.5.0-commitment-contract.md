# v0.5.0 Commitment Contract

## Intent

`ops-tracker v0.5.0 Phase 0 — Commitment Contract` locks the durable boundaries for `v0.5.0` before runtime implementation begins.

Its fixed theme is:

`Operational commitments become actionable exceptions`

Its fixed subtheme is:

`Problems stop being alerts and start becoming work`

`Phase 0` exists to fix:

- what a commitment policy is
- what an exception case is
- which exception kinds and statuses are allowed
- how dedupe and delivery boundaries work
- what order `v0.5.0` implementation must follow
- what `v0.5.0` will not become

This document is a contract for `v0.5.0` implementation phases. It does not claim that the shipped `v0.4.0` runtime already implements these concepts.

## Current repo note

- shipped release remains `v0.4.0`
- current package version remains `0.4.0`
- `v0.5.0` starts docs-first
- `Phase 0` fixes product contract only
- `Phase 0` does not add schema, migrations, UI, delivery channels, or background execution changes

## CommitmentPolicy

`CommitmentPolicy` is the official `v0.5.0` concept for turning an operational expectation into a bounded exception rule.

It is a fixed product model for `v0.5.0`. It is not a generic rule builder, arbitrary automation engine, or free-form expression system.

Required contract fields:

| Field | Contract |
| --- | --- |
| `id` | Stable policy identifier |
| `workspaceId` | Workspace boundary for the policy |
| `name` | Human-readable policy label |
| `scopeType` | One of `WORKSPACE`, `PROJECT`, `TEMPLATE` |
| `scopeId` | Scope identifier matched to `scopeType` |
| `kind` | One of `OVERDUE`, `REVIEW_STALE`, `BLOCKED_STALE`, `UNASSIGNED_STALE`, `RECURRING_FAILED` |
| `thresholdMinutes` | Minute threshold when minute precision is required |
| `thresholdHours` | Hour threshold when hour precision is sufficient |
| `severity` | One of `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `isActive` | Policy activation flag |
| `createdAt` | Creation timestamp |
| `updatedAt` | Update timestamp |

Contract rules:

- exactly one threshold unit is used per policy: `thresholdMinutes` or `thresholdHours`
- supported scope types stay fixed to `WORKSPACE`, `PROJECT`, and `TEMPLATE`
- supported kinds stay fixed to the five `v0.5.0` exception kinds
- supported severities stay fixed to `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL`
- `v0.5.0` does not widen this model into arbitrary predicates, scripting, or custom rule composition

## ExceptionCase

`ExceptionCase` is the `v0.5.0` source-of-truth exception ledger.

It is not a notification row, not a transport artifact, and not a passive alert history line. It is the work object that tells the system and operators what problem exists, who owns it, what state it is in, and whether it is still active.

Required contract fields:

| Field | Contract |
| --- | --- |
| `id` | Stable case identifier |
| `workspaceId` | Workspace boundary for the case |
| `kind` | One of the fixed `v0.5.0` exception kinds |
| `status` | One of `OPEN`, `ACKNOWLEDGED`, `SNOOZED`, `RESOLVED` |
| `severity` | One of `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `sourcePolicyId` | The policy that opened the case |
| `taskId` | Nullable task source when the case is task-based |
| `recurringExecutionId` | Nullable recurring source when the case is recurring-failure-based |
| `ownerId` | Nullable current owner for response work |
| `openedAt` | When the case first opened |
| `acknowledgedAt` | When the case was acknowledged |
| `snoozedUntil` | Nullable snooze-until timestamp |
| `resolvedAt` | Nullable resolution timestamp |
| `resolutionKind` | One of `AUTO`, `MANUAL` |
| `fingerprint` | Stable dedupe key for same-source convergence |
| `title` | Human-readable work title |
| `details` | Structured explanation of why the case exists and what it is attached to |
| `createdAt` | Creation timestamp |
| `updatedAt` | Update timestamp |

Contract rules:

- `ExceptionCase` is the source-of-truth ledger for `v0.5.0` exceptions
- `ExceptionCase` is a work object with owner and status, not a transport message
- `taskId` and `recurringExecutionId` stay nullable because the source depends on exception kind
- `resolutionKind` stays fixed to `AUTO` or `MANUAL`
- title and details are part of the work object, not derived-only presentation sugar

## Fixed exception kinds

`v0.5.0` supports exactly these exception kinds:

- `OVERDUE`
- `REVIEW_STALE`
- `BLOCKED_STALE`
- `UNASSIGNED_STALE`
- `RECURRING_FAILED`

No additional exception kinds are part of the `v0.5.0` contract unless a later contract explicitly changes this list.

## Fixed exception statuses

`v0.5.0` supports exactly these exception statuses:

- `OPEN`
- `ACKNOWLEDGED`
- `SNOOZED`
- `RESOLVED`

Open-work interpretation:

- `OPEN`, `ACKNOWLEDGED`, and `SNOOZED` are active case states
- `RESOLVED` is the closed state

## Invariants

- `ExceptionCase` is the source of truth for operational exceptions
- notifications, Slack, email, inbox rows, and any other delivery are derived from `ExceptionCase`
- delivery channels do not become a parallel source of truth
- same source, same kind, and same policy converge to one open case
- `fingerprint` is the stable dedupe key that represents that same-source, same-kind, same-policy identity
- the system prefers auto-resolve when the underlying condition clears
- manual resolve exists as a supporting operator action, not the primary lifecycle mechanism
- `v0.5.0` is not a generic policy builder
- `v0.5.0` is not a full incident management suite

## Dedupe rule

`v0.5.0` uses a single-case convergence rule:

- at most one non-resolved `ExceptionCase` may exist for the same `workspaceId + fingerprint`
- `fingerprint` must encode the same source, same kind, and same policy identity
- when the same condition is observed again while an active case already exists, the existing case is updated or kept active rather than opening a second open case
- once the case is `RESOLVED`, a future recurrence may open a new case with the same fingerprint

## Delivery boundary

- inbox notifications, Slack messages, email, and any later delivery are downstream projections of `ExceptionCase`
- delivery can be retried, deduped, or expanded without changing the source-of-truth case lifecycle
- `v0.5.0` does not require a full multi-channel delivery matrix

## Implementation order contract

1. `ops-tracker v0.5.0 Phase 0 — Commitment Contract`
2. `ops-tracker v0.5.0 Phase 1 — Commitment Policies`
3. `ops-tracker v0.5.0 Phase 2 — Exception Ledger`
4. `ops-tracker v0.5.0 Phase 3 — Response & Escalation`
5. `ops-tracker v0.5.0 Phase 4 — Release Closeout`

Dependency rule:

- `Phase 1` depends on `Phase 0`
- `Phase 2` depends on `Phase 0` and `Phase 1`
- `Phase 3` depends on `Phase 0`, `Phase 1`, and `Phase 2`
- `Phase 4` closes the delivered scope after `Phase 1`, `Phase 2`, and `Phase 3`

## Acceptance criteria overview

- `ops-tracker v0.5.0 Phase 0 — Commitment Contract`
  - canonical contract doc exists
  - `CommitmentPolicy` and `ExceptionCase` shapes are fixed in repo docs
  - kinds, statuses, invariants, dedupe rule, phase order, and non-goals are fixed
  - shipped `v0.4.0` state and future `v0.5.0` state remain clearly separated
- `ops-tracker v0.5.0 Phase 1 — Commitment Policies`
  - `CommitmentPolicy` becomes a persisted runtime model with the fixed contract shape
  - supported scope types, kinds, severities, and threshold fields remain bounded to this contract
  - policies can be activated or deactivated without widening into a generic builder
- `ops-tracker v0.5.0 Phase 2 — Exception Ledger`
  - `ExceptionCase` becomes a persisted source-of-truth ledger
  - open-case creation covers the five fixed exception kinds
  - dedupe converges same-source, same-kind, same-policy observations into one open case
  - auto-resolve is implemented for cleared conditions and delivery reads from the ledger
- `ops-tracker v0.5.0 Phase 3 — Response & Escalation`
  - operators can acknowledge, snooze, assign, and manually resolve cases
  - escalation and outbound delivery are derived from case state and severity
  - exception work is managed as owned response work, not raw alert spam
- `ops-tracker v0.5.0 Phase 4 — Release Closeout`
  - docs, tests, validation notes, and release notes describe the same delivered `v0.5.0` boundary
  - shipped `v0.4.0` history and delivered `v0.5.0` scope remain clearly separated
  - hosted CI result is observed or blocked explicitly
  - remaining blockers are explicit

## Non-goals

- full incident platform
- generic automation builder
- policy builder UI
- full multi-channel delivery matrix
- advanced SLA prediction
- org hierarchy
- BI or forecasting
- arbitrary custom rule engine

## Explicitly deferred in Phase 0

- `CommitmentPolicy` runtime implementation
- `ExceptionCase` schema or migration
- exception queue UI
- acknowledge, snooze, or resolve UI
- outbound delivery
- GitHub Actions changes
- project-wide refactor
